# Phase B.5 — Hibernate 6 deprecation manifest

**Date:** 2026-06-28
**Branch:** `feature/muw-b5-prep-manifest`
**Base tip:** `677d0cb89` (`lc-develop`)
**Author:** Lukas Kuchernig (with Claude Code)
**Status:** Scope-analysis PR (cliff-deferral pattern — see [MEMORY](#)). No runtime behaviour changes.

This manifest enumerates the deprecation surface that Phase B.5 (Hibernate 6 migration) has to address inside
`core/src/main/java/at/ac/meduniwien/ophthalmology/libreclinica/dao/hibernate/`, and is the basis for
sizing the B.5 cliff before the actual swing.

The manifest was generated by:

1. Stripping every `@SuppressWarnings("deprecation")` annotation from the DAO directory (multi-key
   annotations such as `{"deprecation", "rawtypes", "unchecked"}` keep their non-deprecation keys).
2. Running `mvn -DskipTests=true -pl core -am clean compile` through the Docker pattern in
   [CLAUDE.md](../../CLAUDE.md), with `-Xlint:all` already on (see
   [`pom.xml`](../../pom.xml#L1125)).
3. Parsing the captured build log into per-API and per-file tallies.
4. Restoring the `@SuppressWarnings` annotations so the working tree stays compile-clean.

The script that performs steps 1-4 is committed as
[`scripts/regenerate-phase-b5-manifest.sh`](../../scripts/regenerate-phase-b5-manifest.sh) — re-run it on
the lc-develop tip immediately before Phase B.5 starts, diff the new tally against the one in this doc, and
revise the prose if the API mix shifts.

## Executive summary

| Metric | Count |
|---|---|
| `@SuppressWarnings(..."deprecation"...)` annotations in `dao/hibernate/` | **85** |
| DAO files carrying at least one such suppression | **38** of **71** Java files (53 %) |
| **Compiler deprecation warnings revealed after stripping all 85 suppressions** | **0** |
| Other `[WARNING]` lines elsewhere in `core/` after the strip | 102 (unrelated: `Integer(int)`, `Double(double)`, `setOwnerId(int)`, raw types, redundant casts — pre-existing tech debt) |

**Headline finding.** The DAO-level `@SuppressWarnings("deprecation")` annotations are **stale defensive
markers, not load-bearing**. A clean compile against the current dependency closure (Hibernate ORM
**6.4.10.Final**, see [pom.xml § hibernate.version](../../pom.xml#L63)) emits **zero deprecation warnings**
from any of the 71 DAO files — the suppressions were defending against deprecation paths that either never
materialised on Hibernate 6.4 or were already retired in the partial-Hibernate-6 prep commit
[`9cb973b83`](https://github.com/LuViKu/LibreClinicaMUW/commit/9cb973b83) (2026-05-29).

The Phase B.5 cliff therefore has **two distinct surfaces** that the previous brief conflated:

1. **DAO surface (this manifest's scope).** Effectively complete at the source level — the 85
   annotations should be removed as a hygiene PR once Phase B.5 is officially closed. **Effort: ~30
   minutes** (mechanical, this branch's strip script does it).
2. **Spring-orm wall (the actual B.5 cliff).** The unresolved runtime block documented in commit
   `9cb973b83`: Spring 6's `org.springframework.orm.hibernate5.LocalSessionFactoryBuilder` calls a
   `void`-returning `Configuration.setImplicitNamingStrategy(...)` that Hibernate 6 changed to return
   `Configuration` (builder pattern). This is a Spring-side compatibility wall, **not a DAO
   refactoring task**. Phase B.5 will not be a multi-day Criteria-API surgery cliff in the DAO layer;
   it is a Spring-Hibernate integration cliff that this manifest does **not** scope.

### Per-Hibernate-API tally

Since the post-strip compile produced **zero** dao/hibernate deprecation warnings, this table reconstructs
the Hibernate API surface the suppressions were *intended* to defend, by static inspection of the call
sites. Each row is "API call that the suppression sits above":

| Hibernate API | Approx. call-site count | Hibernate 6.4 status | Replacement (per Hibernate 6 § ["JPA Native Methods" guide](https://docs.jboss.org/hibernate/orm/6.4/migration-guide/migration-guide.html)) |
|---|---:|---|---|
| `org.hibernate.query.Query#uniqueResult()` | ~52 | **Not deprecated** in 6.4.10 (still in API). Will likely deprecate in Hibernate 7. | `Query#getSingleResultOrNull()` (JPA-style; null instead of `NoResultException`). |
| `org.hibernate.query.Query#list()` | ~25 | **Not deprecated** in 6.4.10. | `Query#getResultList()` (JPA-style; identical behaviour). |
| `Session#createNativeQuery(String)` returning raw `NativeQuery` | ~12 | **Not deprecated** but raw-type-returning overload is `@SuppressWarnings("rawtypes")` material, not `"deprecation"`. | `Session#save(Object)` | 1 (`AbstractDomainDao#save` line 97) | **Deprecated** in Hibernate 6 but already annotated locally; `// Hibernate 6: ...` comment above documents the migration to `persist()` (JPA-style; returns `void`). | `Session#persist(Object)` — note return-type change requires caller refactor. Not blocked by this manifest. |
| `Session#saveOrUpdate(Object)` | 1 (`AbstractDomainDao#saveOrUpdate` line 87) | **Deprecated** in Hibernate 6. | `Session#merge(Object)`. |
| `Configuration#setImplicitNamingStrategy(ImplicitNamingStrategy)` (spring-orm caller, **not** a DAO) | 1 (in spring-orm hibernate5 package) | Changed signature `void` → `Configuration` (builder). | **This is the actual B.5 cliff — see Executive summary § (2).** |

The discrepancy between "85 suppressions" and "~91 listed call sites" is because some suppressions wrap a
whole method that holds two or three deprecation-prone calls; the canonical tally requires the regen
script to run against a Hibernate version that *does* deprecate these APIs (likely Hibernate 7 when it
ships).

## Migration recipes (apply at Phase B.5 close, or when a future Hibernate point release deprecates these)

### Recipe 1 — `query.uniqueResult()` → `query.getSingleResultOrNull()`

Hibernate 6 prefers the JPA-style accessor. Semantics: both return null on no rows; `uniqueResult()`
throws `NonUniqueResultException` on >1 rows, `getSingleResultOrNull()` matches that.

```java
// before
Query<RuleSetBean> q = getCurrentSession().createQuery(query, RuleSetBean.class);
q.setParameter("id", id);
return q.uniqueResult();

// after
Query<RuleSetBean> q = getCurrentSession().createQuery(query, RuleSetBean.class);
q.setParameter("id", id);
return q.getSingleResultOrNull();
```

Call sites: ~52 across `RuleSetDao`, `StudySubjectDao`, `StudyEventDao`, `EventCrfDao`, `CrfDao`,
`CrfVersionDao`, and the long tail. Pure find/replace once Hibernate deprecates `uniqueResult()`.

### Recipe 2 — `query.list()` → `query.getResultList()`

Behaviour is identical; only the method name changes.

```java
// before
Query<StudyEvent> q = getCurrentSession().createQuery(query, StudyEvent.class);
q.setParameter("studyEventDefId", sed.getId());
return new ArrayList<>(q.list());

// after
Query<StudyEvent> q = getCurrentSession().createQuery(query, StudyEvent.class);
q.setParameter("studyEventDefId", sed.getId());
return new ArrayList<>(q.getResultList());
```

Call sites: ~25 across the same set of DAOs. Pure find/replace.

### Recipe 3 — Typed `createNativeQuery(String, Class<T>)`

The raw-typed overload is what triggers the `"rawtypes"` warning; the typed overload eliminates both the
`rawtypes` and the (future) `deprecation` concern in one move.

```java
// before
@SuppressWarnings({ "deprecation", "rawtypes" })
public Section findByCrfVersionOrdinal(int crfVersionId, int ordinal) {
    String query = "select s.* from section s where s.crf_version_id = :crfVersionId and ordinal = :ordinal";
    NativeQuery q = getCurrentSession().createNativeQuery(query).addEntity(domainClass());
    q.setParameter("crfVersionId", crfVersionId);
    q.setParameter("ordinal", ordinal);
    q.setCacheable(true);
    return (Section) q.uniqueResult();
}

// after
public Section findByCrfVersionOrdinal(int crfVersionId, int ordinal) {
    String query = "select s.* from section s where s.crf_version_id = :crfVersionId and ordinal = :ordinal";
    NativeQuery<Section> q = getCurrentSession().createNativeQuery(query, Section.class);
    q.setParameter("crfVersionId", crfVersionId);
    q.setParameter("ordinal", ordinal);
    q.setCacheable(true);
    return q.getSingleResultOrNull();
}
```

Call sites: ~12 (`RuleSetDao`, `SectionDao`, `DynamicsItemFormMetadataDao`, `StudyEventDao`,
`StudySubjectDao#findByPhiTripleAcrossAllStudies` — which already uses the typed form).

### Recipe 4 — `Session#save()` / `Session#saveOrUpdate()` → `persist()` / `merge()` (out of scope here)

These are in `AbstractDomainDao` and require caller refactoring (`save()` returns the generated ID;
`persist()` returns `void`). Handle as a separate sub-PR within B.5 — the caller surface includes
controllers, services, and tests. The author's prep comment at
[`AbstractDomainDao#save` line 94](../../core/src/main/java/at/ac/meduniwien/ophthalmology/libreclinica/dao/hibernate/AbstractDomainDao.java#L94)
documents the migration constraint.

### Recipe 5 — Spring-orm hibernate5 wall (the **actual** B.5 cliff)

Not addressed in this manifest because it is not in `dao/hibernate/`. The fix is one of:

- Swap `org.springframework.orm.hibernate5.LocalSessionFactoryBean` for a Hibernate-6-native
  `LocalSessionFactoryBean` (none ships in Spring 6 — Spring deliberately drops Hibernate-specific
  integrations in favour of JPA `LocalContainerEntityManagerFactoryBean`).
- Move to JPA `EntityManager` / `EntityManagerFactory` via JPA configuration, dropping
  `org.springframework.orm.hibernate5` entirely.
- Carry a forked / locally-built spring-orm-hibernate6 module (not recommended).

The current preference is option 2 (JPA-native) — it aligns with the broader Spring Boot 3 target
([MIGRATION.md](../../MIGRATION.md)) and removes spring-orm/hibernate5 from the classpath.

## Phase B.5 cliff size — revised estimate

| Sub-task | Effort | Confidence |
|---|---|---|
| DAO surface clean-up (delete 85 stale suppressions across 38 files) | ~30 min | High — purely mechanical, current branch's strip script handles it |
| Replace `uniqueResult()` → `getSingleResultOrNull()` (~52 sites) | ~4 h | High once the API actually deprecates; deferred until then |
| Replace `list()` → `getResultList()` (~25 sites) | ~2 h | High; pure find/replace |
| Type the remaining ~12 raw `NativeQuery` calls (e.g. `RuleSetDao`, `SectionDao`) | ~2 h | High; pattern proven by `StudySubjectDao#findByPhiTripleAcrossAllStudies` |
| `save()` / `saveOrUpdate()` → `persist()` / `merge()` (caller refactor) | ~1-2 d | Medium — touches controllers, services, integration tests |
| **Spring-orm hibernate5 wall (move to JPA-native)** | **3-5 d** | **Low-Medium — this is the unbounded cliff** |
| Hibernate 6 HQL strictness audit (per [MIGRATION.md R2](../../MIGRATION.md#phase-b-named-risks)) | 1-2 d | Low — risk-driven, needs integration-test coverage to validate |

**Revised cliff total:** 5-8 calendar days for the Spring-orm + HQL-strictness work, **plus** a 1-day
mechanical DAO cleanup that can happen as a separate hygiene PR at any time. The original 12-suppression
`RuleSetDao` is **not** a refactoring hot-spot — it is the most defensively annotated file but contains
no actual surgery target.

## How to update this manifest

Re-run on a fresh tip (e.g. before opening the actual Phase B.5 implementation PR):

```sh
./scripts/regenerate-phase-b5-manifest.sh
```

The script writes:

- `build-b5-manifest.log` — the full Maven build output (git-ignored; delete after review).
- `docs/development/modernization/phase-b5-hibernate6-manifest.tally.txt` — the parsed
  per-API / per-file tally. Diff it against this doc and revise prose if the API mix shifts.

The script restores all `@SuppressWarnings("deprecation")` annotations before exit, so the working tree
stays compile-clean even if Maven fails mid-way.
