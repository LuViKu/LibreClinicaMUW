# Liquibase 4 spike — 2026-09-30

**Verdict: ready.** Liquibase 3.6.3 → **4.31.1** passes all three checks, with two small shims. It is committed on `spike/muw-liquibase-4` as `b03a060f6` and closes CVE-2022-0839. Not pushed.

Liquibase 4 has three incompatibilities with this changelog. Two need a shim and one decides the version:

| # | Incompatibility | Effect without a fix | Fix |
|---|---|---|---|
| 1 | 4.x rejects the seven heritage `modifyColumn` elements in its default STRICT parse mode | the changelog does not parse and the app does not start (the July failure, `1e47ca099` → `ac9cde871`) | `LaxParsingSpringLiquibase`: LAX mode, guarded by `ChangelogElementsTest` |
| 2 | on PostgreSQL 10+, 4.x creates `autoIncrement` columns as `GENERATED BY DEFAULT AS IDENTITY`; 3.6.3 created `serial` | a new database differs from every existing one in 93 columns, and the ITs run on a schema production does not have | `SerialPostgresDatabase` (registered in `META-INF/services`), guarded by an IT assertion |
| 3 | 4.33.0 adds `rawDateValue` to the checksum of every changeset that uses `valueDate` | startup validation fails on every database 3.6.3 built: 4 changesets on a production-context database, 29 with the demo seeds (it fails closed, and the database is untouched) | use **4.31.1**, the version Boot 3.5.16 manages. 4.32.0 validates the same way; 5.x is licensed FSL-1.1-ALv2 |

## 1. What 3.6.3 does with `modifyColumn`

The survey's inference holds. In the 3.6.3 source, `ChangeFactory.create("modifyColumn")` returns `null`, because no class is registered for that name, and `ChangeSet.addChange(null)` returns without a word. So each of the seven changesets runs with no changes.

A fresh 3.6.3 build and the shared dev database agree. All seven are `EXECUTED` with the description `empty` and the checksum `8:d41d8cd98f00b204e9800998ecf8427e`, which is the MD5 of the empty string. The columns show where the intended types came from:

| Element | Asks for | Column on PostgreSQL | Set by |
|---|---|---|---|
| `audit_log_event.old_value`, `.new_value` (2.5) | `VARCHAR(4000)` | 4000 | `lc-1.4.0/audit-log-event-value-length.xml` (`modifyDataType`); `createTable` had 2000 |
| `dataset.sql_statement`, `filter.sql_statement` (2.5) | `VARCHAR(4000)` | `text` | the PostgreSQL `createTable` (`CLOB`); these two elements belong with the Oracle-only variants |
| `study_user_role.user_name` (3.6) | 64 | 64 | `lc-1.4.0/username-length.xml` |
| `authorities.username` (3.6) | 64 | 64 | `lc-1.4.0/username-length.xml` |
| `user_role.role_name` (3.6) | 64 | **50** | nothing: the only one never applied |

So LAX mode reproduces production exactly. `user_role.role_name` stays `VARCHAR(50)`; widening it would be a new `lc-muw-*` changeset and a separate decision.

## 2. The three checks

**(a) From scratch.** The full changelog ran on empty PostgreSQL 14 databases with 3.6.3 and with 4.31.1 (LAX + serial), for both context sets: `!demo` (production) and `demo` (dev compose). `pg_dump --schema-only`, with `databasechangelog*` excluded, is **identical**: 11,331 lines for each set. The only diff lines are pg_dump's random per-dump `\restrict` keys.

The data dumps are identical once `now()` timestamps and `gen_random_uuid()` values are masked. `databasechangelog` holds the same 1,167 (`!demo`) and 1,202 (`demo`) changesets, in the same order, with the same file names and exec types. Without `SerialPostgresDatabase` the schema differs in 93 identity columns, on 4.31.1 and 4.33.0 alike.

**(b) Upgrade path.** Two 3.6.3-built targets were used:

- a copy of the 3.6.3 production-context build;
- a restore of a read-only `pg_dump` of `libreclinica-muw-db-1`, the shared dev database: 1,202 changesets applied incrementally since 2026-07-09, whose stored checksums all equal a fresh 3.6.3 build's.

With 4.31.1:

- **Validation passes, nothing runs.** The update summary is `Run: 0`, with `Previously run: 1167` and `1202`. None of the 28 `runOnChange` changesets re-ran.
- **Only the checksums change.** Schema and data are byte-identical before and after. In `databasechangelog` only `md5sum` changes: each stored `8:` checksum is validated and rewritten as `9:`. Order, dates, exec types and deployment IDs are untouched. A second run changes nothing.
- **The real WAR agrees.** The built WAR ran on `tomcat:10.1-jdk25-temurin` against a fresh restore of the dev copy: `Run: 0 / Previously run: 1202`, health UP, and schema and changelog as above. Its data changes (Quartz triggers, the version row, usage statistics) are on the same tables a 3.6.3 WAR changes on the same copy, plus storage samples from the hourly job, which ran during the longer session. They are the app's own startup writes. A restart ran nothing and upgraded no checksum.
- **A new install from the WAR matches too.** The same WAR installed an empty database (production contexts) with 1,167 changesets, 0 identity columns and 103 serial defaults. Its schema is identical to the 3.6.3 build, so the `ServiceLoader` registration works inside Tomcat's webapp classloader.
- **4.33.0 and 4.32.0.** 4.33.0 fails validation on both targets (4 and 29 changesets, all of them using `valueDate`) and leaves them untouched. 4.32.0 passes like 4.31.1.

## 3. The new tests, red then green

| Test | Red | Green |
|---|---|---|
| `ChangelogElementsTest` (core unit): the only unknown elements in `migration/**` are the seven `modifyColumn` | a temporary, uncommitted changelog holding a misspelt change (`addColum`), a misspelt rollback change (`dropColum`) and a misspelt precondition nested in `<not>` (`tableExist`): fails and names all three | 2 / 2 |
| `LiquibaseChangelogIdempotencyIT.autoIncrementColumnsAreSerialAsOnEveryExistingDatabase` | service registration removed: `expected: <0> but was: <93>` | passes in the 1,410 run |

Without LAX, every DB IT fails at `AbstractApiControllerDatabaseIT`'s Liquibase run with `Unknown change type 'modifyColumn'`; that failure reproduces with the default STRICT mode.

## 4. Rollback: restore the backup, do not redeploy the old WAR

Starting 3.6.3 again on a database that 4.x has touched is **not** clean. 3.6.3 does not recognise `9:` checksums, resets them all, and then treats the 25 applicable `runOnChange` changesets as changed and re-runs them.

On the dev copy this inserted 11 `measurement_unit` rows through the `2009-05-15-3624-3` backfill. It also re-created one trigger function, identical apart from whitespace. On production data other `runOnChange` bodies would run again too. So a rollback of this upgrade means restoring the pre-upgrade backup. The deploy runbook should say so. (This report first also offered restoring only the `databasechangelog.md5sum` column. That was never tested, and any `9:` checksum it leaves behind sets off the same re-runs, so the runbook offers only the full restore.)

## 5. Method (reproducible)

- **Harness.** A 30-line `SpringLiquibase` runner configured as `DataSourceConfig` is (`classpath:migration/master.xml`, the same contexts), run on `maven:3-eclipse-temurin-25` against `postgres:14-alpine` on an isolated network. The classpath was resolved per Liquibase version. LAX was set with `-Dliquibase.changelogParseMode=LAX`; for the serial type, the harness registered the `PostgresDatabase` override with `DatabaseFactory`.
- **Comparisons.** `pg_dump --schema-only` and `--data-only` with `-T databasechangelog -T databasechangeloglock`, plus full `databasechangelog` snapshots before and after each run.
- **Dev database.** Only read from: one `pg_dump -Fc`, restored into the spike's own container.
- **Checksum difference.** Found by printing Liquibase's checksum serialization for changeset `1235684743487-332` under both versions: 4.33.0 adds `rawDateValue="2006-10-23"`. Inspecting the 4.x jars shows the field only in 4.33.0.
